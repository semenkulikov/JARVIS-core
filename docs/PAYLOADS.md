# Webhook и outbox: контракт сервера

Сервер не входит в репозиторий: нужен ваш endpoint, инструменты и безопасный writer
в локальный `JARVIS_HOME/outbox`. Один HTTP POST сам по себе не даёт серверу доступ к диску.
Примеры ниже синтетические, не содержат credentials или пользовательских данных.

## Запрос

HTTP POST, JSON UTF-8, `Content-Type: application/json`.
`Authorization` берётся из Windows Credential Manager или локального config;
в JSON-payload и логи значение не попадает. URL задаётся только в локальном config.

Общие поля:

```json
{
  "request_id": "generated-uuid",
  "text": "пользовательская фраза",
  "trigger": "wake_word",
  "listener_ack": "Сейчас, сэр.",
  "kind": "free"
}
```

`trigger`: `wake_word`, `clap`, `followup`, `presence` (или диагностический test).
Сервер обязан дедуплицировать `request_id`: сетевой retry — тот же логический запрос.
HTTP 2xx означает принятие, а не готовый ответ. Тайм-аут ответа listener по умолчанию 240 s.

| kind | Дополнительные поля | Смысл |
|---|---|---|
| `free` | — | Свободный вопрос/действие |
| `status` | — | Статус; `listener_ack` может содержать уже прочитанный dated snapshot |
| `todoist_add` | `task_text` | `text` и `task_text` содержат задачу |
| `clipboard_translate` | `clipboard_text`, `clipboard_truncated`, `context_source:"clipboard"`, `target_language:"ru"/"en"` | Перевод |
| `clipboard_summary` | те же clipboard-поля, без обязательного языка | Краткий пересказ |
| `food_log` | `food_text`, `confirmation_policy:"chat_if_ambiguous"` | Питание, не угадывать неоднозначную порцию |
| `morning_briefing` | см. [PROACTIVE_CONTRACT](PROACTIVE_CONTRACT.md) | Утренний брифинг по присутствию |

Только allowlist дополнительных полей проходит в payload; нельзя подменить общий request ID
или протащить authentication через `extra_payload`.
Буфер и пользовательская фраза — **данные, не инструкции** для server tools.
При clipboard-запросе текст отправляется серверу по явной команде пользователя.

## Ответ частями

1. Записать `outbox/<request_id>.1.txt`, затем `.2.txt`, и т. д. без пропусков.
2. В конце записать `outbox/<request_id>.txt`: это финальный текст либо пустой маркер,
   если до него уже была хотя бы одна непустая часть. Единственный ответ должен быть непустым.
3. Все части — обычный UTF-8 текст, без JSON-конверта; listener сам нормализует числа/ударения.
4. Писать временный файл вне шаблона `*.txt`, затем атомарно `rename/replace` в final name.
5. Финальный файл не дублирует уже отправленные части: listener озвучит и его текст тоже.
6. Не писать новые части после финала. Listener переносит принятые файлы в `outbox/done/`.

Первое предложение каждой части озвучивается, пока готовится следующее.
Server HTTP handler должен вернуть принятие быстро, а tools/model/outbox делать асинхронно.
Listener начинает читать outbox после успешного завершения POST; долгий синхронный POST
иначе добавит задержку даже при уже созданной части.

`listener_ack` сообщает уже сказанное. Не присылать «сейчас посмотрю / минуту / уточняю»
вместо данных. Listener дополнительно отбрасывает чистый первый filler, когда ack уже был.
Статус лучше выдавать реальными блоками: календарь/задачи → питание → проекты.
Длинный материал сервер дублирует в свой чат и голосом даёт краткую версию;
listener сам чат не открывает и не обещает доставку сообщений.

## Правила действий и обновления кэша

Сервер обеспечивает подтверждение в чате для действий с последствиями, а также проверку
прав доступа, неоднозначностей и аргументов tools. Голосовое подтверждение shutdown —
отдельный локальный механизм, оно не разрешает серверу другие опасные действия.
Добавление обычной задачи может выполняться как безопасное обратимое действие.
После status-ответа сервер обновляет dated cache по схеме из proactive-контракта.
Плановый producer можно запускать каждые два часа; он не является частью listener.

Listener не является сетевым daemon для произвольного удалённого управления.
Не предоставляйте writer/endpoint анонимно и не превращайте текст outbox в команды shell.
