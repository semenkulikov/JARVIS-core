# Вызов сервера и папка outbox

Сервера в репозитории нет. Нужны ваш адрес, ваши инструменты и программа, которая пишет ответы в `JARVIS_HOME/outbox`. Один HTTP POST сам по себе не даёт серверу доступ к диску. Примеры ниже выдуманы: в них нет секретов и чужих данных.

## Запрос

HTTP POST, JSON в UTF-8, заголовок `Content-Type: application/json`. Значение `Authorization` берётся из диспетчера учётных данных Windows или из локальных настроек. В тело запроса и в журнал оно не попадает. Адрес задаётся только в локальном `config.json`.

Общие поля:

```json
{
  "request_id": "generated-uuid",
  "text": "пользовательская фраза",
  "trigger": "wake_word",
  "listener_ack": "Сейчас, сэр.",
  "kind": "free"
}
```

`trigger`: `wake_word`, `clap`, `followup`, `presence`. В тестах бывает ещё `test`. Сервер отбрасывает повторный `request_id`: повтор по сети — тот же запрос. Ответ HTTP 2xx значит «принято», а не «ответ готов». Помощник ждёт текст по умолчанию 240 секунд.

| `kind` | Дополнительные поля | Смысл |
|---|---|---|
| `free` | — | Свободный вопрос или действие |
| `status` | — | Статус. В `listener_ack` уже может быть прочитанный снимок с датой |
| `todoist_add` | `task_text` | В `text` и `task_text` одна и та же задача |
| `clipboard_translate` | `clipboard_text`, `clipboard_truncated`, `context_source` = `clipboard`, `target_language` = `ru` или `en` | Перевод |
| `clipboard_summary` | те же поля буфера, язык не обязателен | Краткий пересказ |
| `food_log` | `food_text`, `confirmation_policy` = `chat_if_ambiguous` | Питание. Неоднозначную порцию не угадывать |
| `morning_briefing` | см. [контракт объявлений](PROACTIVE_CONTRACT.md) | Утренний брифинг, когда человек у компьютера |

В запрос попадают только поля из этого списка. Подменить `request_id` или протащить секрет через лишние поля нельзя. Фраза и буфер обмена — данные для сервера, не команды его инструментам. Текст буфера уходит на сервер только по явной голосовой команде.

## Ответ частями

1. Записать `outbox/<request_id>.1.txt`, затем `.2.txt` и дальше без пропусков.
2. В конце записать `outbox/<request_id>.txt`. Это последний кусок или пустая метка, если до неё уже была хотя бы одна непустая часть. Единственный ответ должен быть непустым.
3. Все части — обычный текст UTF-8, без JSON-обёртки. Числа и ударения помощник поправляет сам.
4. Писать временный файл, чьё имя не оканчивается на `.txt`, и затем атомарно переименовать его в окончательное.
5. Последний файл не повторяет уже отданные части: его текст тоже будет озвучен.
6. После последнего файла новые части не писать. Принятые файлы помощник переносит в `outbox/done/`.

Первое предложение каждой части звучит, пока готовится следующее. Обработчик HTTP должен быстро ответить «принято», а модель и запись файлов делать дальше отдельно. Помощник начинает читать `outbox` после успешного POST. Долгий синхронный POST добавит задержку, даже если файл уже лежит на диске.

Поле `listener_ack` — это фраза, которую помощник уже сказал. Не присылайте вместо данных «сейчас посмотрю», «минуту» и «уточняю». Если короткая реплика уже была, пустую первую отписку помощник отбрасывает. Статус лучше отдавать блоками: календарь и задачи, затем питание, затем проекты. Длинный текст сервер дублирует в свой чат, а голосом даёт краткую версию. Помощник чат не открывает и доставку сообщений не выполняет.

## Действия и обновление кэша

Действия с последствиями сервер подтверждает в чате и сам проверяет права, неоднозначности и аргументы инструментов. Голосовое «да» на выключение компьютера разрешает только это локальное выключение. Обычную задачу можно добавить сразу: её можно отменить.

После ответа на статус сервер обновляет снимок с датой по схеме из [контракта объявлений](PROACTIVE_CONTRACT.md). Отдельный планировщик на сервере можно запускать каждые два часа. К помощнику он не относится.

Помощник не принимает произвольные команды из сети. Не открывайте запись в `outbox` и адрес сервера без проверки. Текст из `outbox` не превращайте в команду оболочки.
